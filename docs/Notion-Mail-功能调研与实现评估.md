# Notion Mail 功能调研与实现评估（学校邮箱复刻版）

> **说明（现状）**：本文是早期（P0/只读阶段）的设计与调研文档，当时只做只读收信；
> 当前版本已支持**发信**（回复 / 转发 / 新写 / 草稿，SMTP + XOAUTH2 或个人邮箱 SMTP），
> 收信侧仍保持只读（不改动服务端邮件）。功能现状以 README 与使用说明为准。

> 目标：复刻 Notion Mail 的核心产品体验，用于**香港中文大学（学校）邮箱**的登录与日常使用。
> 技术底座：「设备码 + XOAUTH2 + Thunderbird 公共 Client ID」免注册只读方案（关键常量与硬约束已内联进 `dev-handoff-school-mail-mvp.md` §2/§3），读写能力按需升级到 Graph API。
> 本文件为**需求/范围/审批用功能清单**，每项标注难度与是否需要写权限。**技术实现规范以 `dev-handoff-school-mail-mvp.md` 为准**，两文档冲突时以后者为准。

## 2. 产品概述

Notion Mail 的差异化在于三点：

1. **AI 原生**：写作自动补全、一键生成/回复、总结线程、用自然语言问收件箱。
2. **像 Notion 一样的邮箱**：收件箱是一个可自定义的「视图」，可按发件人/日期/状态/内容筛选排序。
3. **极速搜索**：Skiff 团队带来的全文检索与轻量架构。

对 学校 复刻而言，我们把它拆成「邮箱连接层」和「产品功能层」。邮箱连接层复用已给出的 Exchange Online 技术路径；产品功能层按下面清单评估。

## 3. 功能清单与实现评估

难度定义：
- **★☆☆ 简单**：纯前端/本地逻辑，1–3 天量级。
- **★★☆ 中等**：需要 IMAP/MIME 解析、同步状态机或第三方 AI API 接入，3–7 天量级。
- **★★★ 困难**：需要服务端写权限、复杂同步一致性或权限审批，1–2 周量级。
- **★★★★ 很高**：需要学校 IT 授权、自注册应用或跨系统深度集成，且有外部阻塞风险。

### E. AI 功能（Notion Mail 差异化核心）

> AI 功能均**不依赖邮箱写权限**，用本地邮件语料 + 外部 LLM API 即可实现，是首期性价比最高的部分。

> 模型选型：运行时文本/Agent 用 `deepseek-v4-pro`；开发 AI 自测看图用 `deepseek-v4-flash-vision-exp`（多模态、V4-Flash 价格、每图最多 384 token）。旧模型名 `deepseek-chat`/`deepseek-reasoner` 已弃用（2026-07-24 停用）。详见 `dev-handoff-school-mail-mvp.md` §3.1/§11。

## 4. 学校 场景关键结论

1. **读侧全绿**：登录、同步、阅读、搜索、AI 总结/撰写、稍后提醒、自定义视图均可按已给技术路径落地，无需注册 Azure 应用、无需联系 IT。
2. **写侧是分水岭**：发信、回复、归档、删除、已读、服务端标签必须获得写权限。三条路：
   - **A. 自注册 Entra + Graph（Mail.ReadWrite / Mail.Send）**：功能最完整，但 学校 租户可能需要管理员同意（`admin consent`）。
   - **B. SMTP AUTH 发送**：部分 M365 租户仍支持，但微软全面禁用 Basic Auth 后风险高，需实测 学校 是否放行。
   - **C. 首期只做本地读侧 + 本地状态**：把「发送」做成二期，或先外接用户自己的发信渠道。
3. **推荐范围（MVP）**：A1–A4 + B1–B7、B9–B12 + C1（编辑器）、C4、C7 + D1–D4 + E1–E7 + F1–F4 + G1、G3–G5。
4. **已拍板（见 `dev-handoff-school-mail-mvp.md` §1）**：范围=方案三（登录+收件箱+AI 总结/搜索问答）；AI=DeepSeek API；客户端=Windows 桌面（Electron）。写侧（C2 发送等）**不纳入首期**，作为二期。
